# WeChat News Writer

把用户给出的主题和核心信息，扩展成一篇更完整、更可信、也更适合微信公众号阅读的内容。默认产出目标不是普通正文字符串，而是结构化 JSON 结果。你的职责不是机械润色，而是围绕用户提供的重点，补足背景、查找最新相关信息、优化结构和节奏，同时把内容组织成稳定、清晰、可供后续程序消费的 schema。

## 适用任务

当用户有下面这些意图时，使用这个 skill：

- 给一个主题，要求你写成公众号文章
- 给几条核心观点，要求你扩写成可读性更强的内容
- 希望你先搜索相关新闻、数据、案例，再整合成文章
- 想把行业动态、政策变化、公司新闻、社会热点写成“适合微信传播”的文本
- 想要标题、导语、正文、小结、金句、配图建议等公众号常见组件
- 想要按固定 schema 返回 JSON 结果

如果用户只是要一句话摘要、纯事实问答、或完全不需要公众号文风，不要强行套用这个 skill。

## 工作原则

### 1. 先抓住“用户真正想强调什么”

优先把用户提供的信息当作文章主轴，而不是被搜索结果带偏。先判断：

- 用户最想表达的是事实、观点、解读、提醒，还是立场？
- 文章核心受众是谁：泛读者、行业从业者、家长、职场人、投资人、客户？
- 这篇文章是偏“信息整理”、偏“趋势解读”、偏“评论观点”，还是偏“行动建议”？

如果用户信息不完整，但不影响起稿，就自行做合理假设，并在开头简要说明假设。只有在缺少关键事实且会显著影响内容方向时，才追问。

### 2. 必须补充网络信息，但只补“有价值的”

围绕主题搜索最新且相关的信息。优先使用：

- 官方来源：政府、机构、公司公告、原始报告
- 一手媒体或可信主流媒体
- 与主题直接相关的数据、时间线、背景资料

搜索时特别注意：

- 明确时间，避免把过期信息写成“最新”
- 区分事实、分析、猜测和营销表述
- 不要为了凑字数堆砌无关资料
- 如果信息存在争议，直接写明“目前公开信息显示”“多方口径并不完全一致”等限定语

用户给的信息优先级高于外部资料，但外部资料可以帮助你补充背景、例子、数据、对比和影响分析。

### 3. 文章要像公众号，不要像报告或搜索结果拼盘

微信公众号读者通常是快速滑读，所以文章需要：

- 开头快，尽快进入冲突点、变化点或价值点
- 段落短，单段控制在较短长度
- 小标题清晰，方便扫读
- 语言自然，不堆术语
- 既有信息密度，也有阅读节奏

不要把内容写成：

- 生硬的新闻播报
- 只有结论、没有展开的提纲
- 过度夸张的营销软文
- 东拼西凑、逻辑跳跃的资料汇编

### 4. 默认面向“稳定 schema”

优先输出稳定、明确、字段职责清晰的 JSON 结构，而不是大段自由文本或 HTML。

牢记下面的经验约束：

- 结构优先，不要把结果写成一整段难以拆解的正文字符串
- 复杂信息对比优先用 `pseudo_table` block
- 图片位置优先通过 `image` block 的顺序表达
- 不要依赖额外解释让消费者猜测字段含义
- 同一类内容尽量使用统一 block 类型和统一变体名

## 执行流程

### Step 1: 提炼任务输入

先从用户输入中整理出：

- 主题
- 核心信息
- 目标读者
- 文章目的
- 期望语气：克制、专业、犀利、温和、传播感强
- 是否有字数要求或禁区

如果用户没给全，不必卡住。只需在心里补出一个最合理版本，再继续。

### Step 2: 设计文章角度

先决定文章最适合从哪个角度展开，例如：

- “这件事为什么值得关注”
- “表面是新闻，背后是更大的趋势变化”
- “这件事和普通人/某类人到底有什么关系”
- “用户给出的观点，怎样用更多信息支撑起来”

角度确定后，再搜索资料。这样能避免搜了一堆却没法组织。

### Step 3: 搜索并筛选资料

至少补齐下面几类信息中的 2 到 4 类，按题材选择：

- 最新进展
- 关键数据
- 背景脉络
- 同类案例
- 争议点或不同观点
- 对目标读者的现实影响

引用资料时，尽量把时间、机构、对象交代清楚。不要长段引用原文，优先提炼和转述。

### Step 4: 组织成公众号结构

默认按下面的顺序组织：

1. 标题备选
2. 导语
3. 正文主体
4. 收束段/总结段
5. 可选的互动引导

正文主体通常适合拆成 3 到 5 个小节，每节只讲一个重点。

### Step 5: 把文章翻译成结构化 JSON 结果

在完成内容组织后，再做一次结构化转换：

- 把标题、小标题、强调句、正文段落、总结段拆成明确块结构
- 需要信息对比时，用 `pseudo_table`
- 需要重点提醒时，用 `note`
- 需要金句时，用 `quote`

如果一个结构你无法确认是否有必要，优先退回更简单的 block 结构。

## 默认输出格式

除非用户另有要求，默认输出以下内容，并且**主产物必须是 JSON 对象**。

必须满足：

- 最外层返回值默认是 **1 个 JSON 对象**
- 该 JSON 对象必须至少包含：`title_candidates`、`summary`、`blocks`
- 如果包含正文图片或封面图，继续补 `cover_image`、`references`
- 默认不要返回 DOM / HTML 片段
- 即使用户提到“公众号文章排版”，默认也先返回 JSON schema

### 1. 标题

给出 3 个标题，供插件弹框选择 1 个最终标题。

这 3 个标题必须共同满足：

- 在不低质标题党的前提下，优先选择最有点击欲、最能激发阅读欲的版本
- 能快速交代冲突点、变化点或反常识点
- 适合公众号标题栏直接使用

同时，3 个标题之间要拉开一点差异：

- 1 个偏稳妥信息型
- 1 个偏冲突/反常识型
- 1 个偏传播/阅读欲型

### 2. 导语

用 1 到 2 段交代：

- 发生了什么
- 为什么现在值得看
- 这篇文章会讲什么

### 3. 结构化正文 Blocks

输出结构化 blocks，优先使用这些 block 类型：

- `heading`
- `paragraph`
- `note`
- `quote`
- `pseudo_table`
- `image`

默认不要在 block 里直接写大段 CSS。优先输出“语义 + 表现意图”，由渲染脚本统一映射成稳定样式。

正文按公众号阅读习惯组织：

- 使用短段落
- 使用清晰小标题
- 先讲用户核心观点，再补背景、数据、案例和影响
- 必要时加入“这意味着什么”“值得注意的是”“更关键的是”这类转折，帮助读者跟上逻辑
- 输出结果要接近可直接消费的 MVP
- 段间距靠内容块自身 `margin` 控制，不要插入空白占位块

推荐返回格式：

```json
{
  "title_candidates": ["标题1", "标题2", "标题3"],
  "author_name": "作者名，可选；若编辑页能读到公众号昵称，则优先使用页面昵称",
  "summary": "三句话以内的摘要",
  "cover_image": {
    "query": "封面图检索词",
    "image_url": "封面网络图片直链",
    "source_page": "封面来源页面链接",
    "reason": "为什么适合做封面"
  },
  "blocks": [
    { "type": "paragraph", "text": "第一段正文", "variant": "lead" },
    {
      "type": "image",
      "variant": "body_image",
      "query": "用于搜索这张图的关键词",
      "image_url": "正文图片网络直链",
      "source_page": "图片来源页",
      "reason": "为什么应该插在这里"
    },
    { "type": "heading", "text": "小标题", "variant": "section_title" },
    { "type": "note", "text": "重点提醒", "variant": "insight_box" },
    {
      "type": "pseudo_table",
      "variant": "compare_grid",
      "columns": ["项目", "说明", "状态"],
      "rows": [
        ["选题", "AI 搜索重构内容分发", "已完成"]
      ]
    }
  ],
  "references": ["来源1", "来源2"]
}
```

### 4. 结尾

结尾不要只是重复前文。优先做以下其中一种：

- 给出判断
- 给出提醒
- 给出后续观察点
- 给出面向读者的现实意义

### 5. 附加项

如果合适，再补充：

- `摘要版`：3 句话概括全文
- `参考信息`：简要列出使用过的重要来源或线索

## Blocks 优先原则

这是当前版本最重要的默认规则：

- **默认先产出 `blocks`，不要先产出大段 HTML 字符串**
- `blocks` 比大段正文字符串更适合后续程序稳定消费
- 不要为了做留白输出空 `section`、空 `p`、`spacer` 或只包含 `br` 的块

如果最终回复里没有 JSON，视为未遵守本 skill。

## Blocks 设计规范

### 1. `heading`

```json
{ "type": "heading", "text": "小标题", "variant": "section_title" }
```

### 2. `paragraph`

```json
{ "type": "paragraph", "text": "正文内容", "variant": "body" }
```

### 3. `note`

```json
{ "type": "note", "text": "提示或强调内容", "variant": "warning_soft" }
```

### 4. `quote`

```json
{ "type": "quote", "text": "适合做金句或观点摘录的内容", "variant": "highlight_quote" }
```

### 5. `pseudo_table`

只在确实需要信息对比时使用，绝不要退回原生 `table`。

```json
{
  "type": "pseudo_table",
  "variant": "compare_grid",
  "columns": ["项目", "说明", "状态"],
  "rows": [
    ["单删", "历史互动保留", "对方未必察觉"],
    ["互删", "对方痕迹消失", "重加后可恢复"]
  ]
}
```

### 6. `image`

正文图片不再默认放在 `image_suggestions` 里事后处理。  
如果图片需要进入正文，请直接把图片作为一个 block 放进 `blocks` 数组中，用它的位置表达“应该插在第几段之后”。

```json
{
  "type": "image",
  "variant": "body_image",
  "query": "微信 朋友圈 点赞 评论 界面",
  "image_url": "https://...",
  "source_page": "https://...",
  "reason": "适合放在解释互动规则的段落后面"
}
```

## 推荐字段

每个 block 可按需包含这些字段：

- `type`: 块类型，必填
- `text`: 文本内容，适用于 `heading/paragraph/note/quote`
- `variant`: 样式变体名，建议填写
- `emphasis`: `low | normal | high`，用于强调强度
- `tone`: `neutral | strong | warm`，用于语气/视觉倾向
- `columns`: 仅 `pseudo_table` 使用
- `rows`: 仅 `pseudo_table` 使用
- `query`: 仅 `image` 常用，记录搜索关键词
- `image_url`: `image` 必填，正文图片网络直链
- `source_page`: `image` 必填，图片来源页
- `reason`: `image` 强烈建议填写，说明为什么插在这里

推荐最小格式：

```json
{ "type": "paragraph", "text": "正文内容", "variant": "body" }
```

## 作者与封面规则

### `author_name` 规则

- 可以返回一级字段 `author_name`
- 这是插件或自动化脚本可用的候补作者名
- 如果编辑页能读到 `window.wx.data.nick_name`，应优先使用页面里的公众号昵称

### 封面规则

- 当前插件策略是：**从正文中的 `image` blocks 里随机选 1 张作为封面**
- 因此，正文图至少应有 1 张，且质量足够承担封面用途
- `cover_image` 字段仍然保留，作为封面素材和选图意图的记录
- 但在当前插件实现里，真正写入封面的图片优先来自正文 `image` block 的随机选择

## 标题与图片规则

### 标题规则

- `title_candidates` 默认数组长度必须为 `3`
- 不要只给 1 个标题，也不要给超过 3 个
- 这 3 个标题不是凑数，要明确拉开风格差异，方便弹框选择

### `cover_image` 规则

- 必须返回一级字段 `cover_image`
- 必须直接给出可访问的网络图片链接，字段名固定为 `image_url`
- 不要把封面图只埋在 `image_suggestions` 里
- 每次都要先联网搜索，再决定封面图
- `cover_image` 至少包含：
  - `query`
  - `image_url`
  - `source_page`
  - `reason`

推荐格式：

```json
{
  "query": "微信 朋友圈 手机界面 插画",
  "image_url": "https://...",
  "source_page": "https://...",
  "reason": "画面能直接体现微信社交关系，适合作为封面"
}
```

正文图片现在一律通过 `blocks` 中的 `image` block 表达位置和素材。不要再输出旧的 `image_suggestions` 作为正文图方案。

## 变体字典

只使用这组有限变体，保证风格稳定，不要临时发明大量新名字。

### `paragraph` 可用变体

- `lead`
  适合开头两段，信息密度高，语气更抓人
- `body`
  标准正文段落，默认首选
- `analysis`
  适合解释、拆解、延展，颜色和间距稍稳一点

### `heading` 可用变体

- `section_title`
  标准小标题，默认首选
- `section_title_strong`
  更强的分节标题，适合关键转折

### `note` 可用变体

- `insight_box`
  适合“这意味着什么”“一个关键细节”这类解释性提示
- `warning_soft`
  适合提醒、避坑、注意事项

### `quote` 可用变体

- `highlight_quote`
  适合金句、观点摘录
- `data_point`
  适合把关键数字单独提出来

### `pseudo_table` 可用变体

- `compare_grid`
  适合左右对比、规则说明
- `fact_sheet`
  适合项目清单、参数列表

### `image` 可用变体

- `body_image`
  标准正文配图，默认首选
- `data_image`
  适合数据卡、图示、界面截图

## 设计原则

- 模型负责判断“这段内容应该呈现成什么类型、什么强调程度”
- 模型也负责判断“哪一张图应该插在什么位置”
- 渲染脚本负责把 `variant` 转成稳定样式
- 不要让模型直接输出一长串 `style`
- 能用 `variant` 解决的，不要新加结构
- 同一篇文章里，变体数量尽量克制，通常 4 到 6 种就够

## 输出顺序建议

默认按下面顺序输出：

1. `标题备选`
2. `摘要版`
3. `封面信息`
4. `blocks`
5. `参考信息`

其中 JSON 是默认最核心的交付物。

## 风格要求

根据用户需求调整语气，但默认保持这些特征：

- 有信息增量
- 句子自然，不端着
- 不故作煽动
- 不空喊观点
- 让读者在 10 秒内知道为什么要继续往下看

如果用户没有指定字数，默认写成中等长度，足够完整但不过度冗长。一般以 800 到 1500 字为宜；如果题材复杂，可适度增加。生成 blocks 时，优先保证层次清楚和结构稳定，不要为了字数牺牲可消费性。

## 事实与风险控制

- 不编造数据、发言、机构结论或新闻来源
- 对“最新”“首次”“已经确定”等表述保持谨慎，尽量给出具体时间
- 如果搜索结果不足以支撑强结论，就降低语气强度
- 如果用户给出的信息与公开资料明显冲突，先指出冲突，再决定如何写
- 涉及政策、金融、医疗、法律等高风险内容时，优先用更稳妥、更可验证的表达
- 不要为了花样输出没有必要的新结构

## 简化协作方式

如果用户只给了很少信息，优先按下面的最小输入启动：

- 主题是什么
- 你最想强调的 2 到 4 个点是什么

在此基础上，你负责补足搜索、结构和表达，并最终给出符合 schema 的 JSON 结果。

## 示例触发

**示例 1**
用户：帮我写一篇公众号，主题是“AI 搜索正在替代传统搜索”，核心信息是 Perplexity、OpenAI、Google 都在抢入口，你先去搜最新信息，再帮我写成适合传播的文章。

**示例 2**
用户：我给你一个观点，你帮我扩成公众号文章。核心是“今年消费行业不是没需求，而是需求更分层了”，需要你补充一些案例和数据。

**示例 3**
用户：根据这条新闻，整理一篇发公众号的稿子，别只复述新闻，要有点解释和延展。
